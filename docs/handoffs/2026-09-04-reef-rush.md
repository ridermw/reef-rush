## Task 6 implementation checkpoint

Goal: load validated course data into an owned physics lifecycle without
coupling it to React or creating the playable renderer early.

Design decisions:

- Use the installed Zod package for version 1 course definitions and inferred
  TypeScript types. Require finite vectors, positive dimensions, valid
  rotations, unique object IDs, a spawn, ordered checkpoint data, optional
  pearl data, and generated visual metadata. Reject malformed data before
  allocating physics resources.
- Keep geometry and obstacles declarative. Support static boxes and spheres,
  bounded current volumes, and rotating solid gates. Reuse gameplay collision
  groups and the compatible Rapier runtime; do not reintroduce snapshots.
- Use an explicit dynamic import registry. Initially register only generated
  Sunlit Shoals. Known courses not built yet, unknown IDs, malformed modules,
  and import failures must produce clear errors rather than silent substitutes.
- A course runtime owns only its colliders, bodies, and obstacles, never the
  caller's physics world. Disposal is idempotent. Construction failure unwinds
  all allocations, including partial obstacle construction, then propagates
  the error. Do not delete unrelated world objects.
- Currents add together inside inclusive box volumes and contribute zero
  outside. Gate updates use bounded accumulated angles and publish live
  kinematic transforms before fish queries. Invalid time values fail clearly;
  zero time does not advance the gate.
- Keep Sunlit Shoals generated. The other two course layouts, progression,
  scene assembly, art, and audio remain in their later tasks.

Implementation order and intended files:

1. `src\game\course\courseDefinition.ts` and
   `tests\unit\courseDefinition.test.ts`: validation and inferred types.
2. `src\content\courses\sunlitShoals.ts`,
   `src\game\course\loadCourseDefinition.ts`, and
   `tests\unit\loadCourseDefinition.test.ts`: one honest generated course and
   explicit loading errors with no eager course import.
3. `src\game\obstacles\Obstacle.ts`, `CurrentVolume.ts`, and `RotatingGate.ts`,
   with focused current and gate tests: update, sampling, and disposal
   contracts independent of React and rendering.
4. `src\game\course\createCourseRuntime.ts` and
   `tests\integration\courseRuntime.test.ts`: allocation, update, sampling,
   cleanup, and rollback using real Rapier worlds.
5. Observe failing regressions before implementing each behavior, then run the

   Task 5 physics regressions. One independent Rubber Duck gate checks spec
